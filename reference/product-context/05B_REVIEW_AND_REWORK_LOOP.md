# 05B. Review, Rejection and Rework Loop

> **상태**: 이 문서는 목표 스펙이다. 원래 구현체(`vibeoffice/`)는 삭제됐고, `apps/api`가 다른 메커니즘으로 점진적으로 재구현 중이다(예: 부서 stage 게이트, 2026-08-06). 이 문서의 규칙이 전부 현재 코드에 집행되는 건 아니다 — 특히 이 파일이 서술하는 Gate/handoff 세부 로직은 아직 미구현이다.

## 1. 왜 필요한가

부서를 한 방향으로만 통과시키면 잘못된 기획이 디자인·기술·코드까지 증폭된다.

따라서 검수부는 문제를 발견하면 전체 프로젝트를 다시 생성하지 않고 **문제의 소유 부서로 최소 범위 반송**한다.

## 2. Finding 구조

```json
{
  "findingId": "RF-001",
  "severity": "blocker",
  "category": "ux",
  "ownerDepartment": "design",
  "title": "분석 결과 화면에서 다음 행동이 없음",
  "evidence": ["SCR-005", "preview/result"],
  "impact": "사용자 흐름이 종료되고 핵심 가치가 완성되지 않음",
  "requestedChange": "결과에서 재연습 또는 개선 과제로 이동",
  "affectedArtifacts": [
    "USER_FLOWS.md",
    "SCREEN_SPEC.md",
    "prototype"
  ],
  "autoFixable": false
}
```

## 3. 문제 귀속

| 문제 | 기본 소유 부서 |
|---|---|
| 사용자·문제·범위 | 기획부 |
| 정보 구조·화면·상태 | 디자인부 |
| API·DB·인증·아키텍처 | 기술설계부 |
| 코드·빌드·테스트 | 개발부 |
| 파일 누락·인계 형식 | 출고부 |

## 4. 재작업 범위

### Local Rework

한 파일 또는 한 화면 수정.

예: 오류 상태 누락.

### Cross-artifact Rework

여러 산출물 정렬.

예: 기능 이름 변경으로 화면·API·작업·테스트 갱신.

### Upstream Rework

상위 기획 결정 변경.

예: 로그인 제거로 사용자 기록 기능이 mock으로 변경.

### Structural Replan

현재 지원 템플릿으로 구현 불가.

예: 단순 CRUD 템플릿으로 실시간 다중 협업 요구.

## 5. 반송 루프

```text
QA Finding
→ 영향 분석
→ 소유 부서 지정
→ 영향 산출물 stale
→ 최소 수정
→ 해당 Gate 재검사
→ 하위 산출물 자동 정렬
→ QA 재검수
```

## 6. 자동 수정 허용

자동:

- ID·링크 누락
- 문서 형식
- 기능명 동기화
- stale 표시
- 테스트 명령 표기
- 명확한 단순 누락

승인 필요:

- Must/Later 변경
- 사용자 흐름 변경
- 기술 스택 변경
- 데이터 삭제
- 인증·권한 변경
- 외부 비용 발생
- 배포

## 7. 반복 제한

같은 Finding이 2회 반복되면:

1. 현재 부서의 자동 수정 중단
2. 상위 산출물 충돌 조사
3. 더 강한 Reviewer 또는 사람 판단
4. 지원 범위 밖 여부 판정

무한 에이전트 대화를 허용하지 않는다.

## 8. 사용자 표시

```text
검수에서 2개 문제가 발견되었습니다.

자동 수정
✓ 화면과 작업의 기능명 불일치

확인 필요
! 로그인 제거 시 사용자별 기록이 사라집니다.
  추천: 데모 기간에는 브라우저 저장으로 대체

[추천대로 수정] [로그인 유지] [영향 보기]
```
