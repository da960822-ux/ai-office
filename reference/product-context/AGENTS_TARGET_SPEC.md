# AGENTS.md — VibeOffice 개발 지침

## 제품 목적

비전공 부트캠프 참여자의 거친 아이디어를 다음 결과로 변환한다.

1. 현실적인 MVP 범위
2. 실행 가능한 기본 UI 시안
3. 요구사항·사용자 흐름·작업·검증 기준
4. Codex 또는 Claude Code용 인계 패키지

이 프로젝트는 범용 자율 에이전트, 완전한 IDE, 무제한 앱 생성기, 코딩 교육 플랫폼을 동시에 만들지 않는다.

## 우선순위

1. 사용자가 복잡하게 명령하지 않아도 되는가
2. 결과가 실제 다음 개발 행동으로 이어지는가
3. 범위·화면·문서·작업이 일치하는가
4. 실패를 검증하고 되돌릴 수 있는가
5. 초보자가 상태와 다음 행동을 이해하는가
6. 에이전트 오피스의 시각적 재미

## 작업 시작 절차

1. 현재 저장소 구조·스택·실행·테스트 명령을 조사한다.
2. `product-context/README_FOR_CODEX.md`와 관련 명세를 읽는다.
3. `GAP_ANALYSIS.md`에 이미 구현됨/누락/충돌/재사용 대상을 기록한다.
4. 가장 작은 수직 슬라이스를 선정한다.
5. 구현 전 성공 조건을 적는다.
6. 구현 후 빌드·테스트·핵심 흐름을 검증한다.

기존 코드가 있으면 전면 재작성하지 않는다. 사용자 변경을 덮어쓰지 않는다.

## 제품 동작 원칙

- 빈 채팅창만 보여주지 않는다.
- 자유 입력에서 프로젝트 유형, 사용자, 목표, 기간, 데이터 필요 여부를 추론한다.
- Quick Draft의 필수 질문은 최대 3개를 목표로 한다.
- 모든 질문에 `추천값으로 진행`, `모름`, `나중에 결정`을 제공한다.
- 기술 선택에는 추천 이유와 변경 가능 여부를 표시한다.
- 에이전트의 긴 대화 대신 결정·근거·산출물·차단 이유를 보여준다.
- 위험 작업, 삭제, 외부 전송, 비용 발생, 배포에는 승인 경계를 둔다.
- 오류는 쉬운 설명, 영향, 재시도, 기술 세부 순서로 표시한다.

## P0 기능

- 쉬운 프로젝트 시작
- 적응형 최소 질문
- 프로젝트 블루프린트
- MVP 범위 보호
- 기본 시안
- 산출물 허브
- 작업 목록
- 자동 검토
- 결정 기록
- 체크포인트와 롤백
- Codex·Claude 인계 ZIP
- 초보자 오류 설명

P0 전에는 스킬 마켓, 완전 자율 운영, 마케팅 자동화, 3D 오피스를 우선하지 않는다.

## 코드 품질

- 모델 응답은 구조화 스키마로 검증한다.
- loading/empty/success/partial/error 상태를 분리한다.
- 대화 기록만을 프로젝트 상태의 원천으로 사용하지 않는다.
- 산출물 버전과 의존성을 추적한다.
- 실패를 정상 상태로 보고 부분 재시도와 복구 경로를 둔다.
- 비밀키를 클라이언트나 내보내기 파일에 포함하지 않는다.
- 파괴적 명령은 명시 승인 없이 실행하지 않는다.

## 검증

- 공식 빌드와 테스트 명령
- 대표 사용자 흐름
- 스키마 유효성
- 새로고침 후 상태 유지
- 실패 후 재시도
- 기본 키보드 접근성과 반응형
- 산출물 간 기능명·범위·필드 일치

## 완료 보고

1. 구현한 사용자 가치
2. 변경 파일
3. 검증 결과
4. 알려진 제한
5. 다음으로 구현할 가장 작은 수직 슬라이스

## 부서형 제품 워크플로

```text
Planning
→ Design
→ Architecture
→ Build
→ QA
→ Shipping
→ Codex·Claude Refinement
```

각 부서는 승인된 입력 버전과 명확한 출력 계약을 사용한다.

- Planning: 제품·범위·roadmap
- Design: 흐름·화면·시안
- Architecture: API·Data·기술 작업
- Build: 빌드 가능한 70점대 MVP
- QA: 기획·UX·기술·실행 검수와 반송
- Shipping: H4/H5 Agent-ready Project Folder

부서 간 채팅 요약만 넘기지 않는다. `handoff.json`과 승인된 산출물 버전을 넘긴다.

## 반송 원칙

- 범위 문제 → Planning
- 흐름·화면 → Design
- API·DB·아키텍처 → Architecture
- 코드·빌드·테스트 → Build
- 파일·인계 형식 → Shipping

전체 재생성보다 최소 영향 수정과 stale 전파를 우선한다.

## 내부 MVP 기준

내부 개발부는 완성형 SaaS를 만들지 않는다.

반드시:

- 핵심 가치 작동
- 공식 build 성공
- mock 경계 명확
- loading·empty·error
- smoke 또는 E2E
- PROJECT_STATUS·BUILD_REPORT
- Codex가 재설계 없이 개선 가능한 구조
