# PM 케이스 스터디: AI Office (Corporate OS v6.2)

## Quick Facts

- **역할**: 기획 · 아키텍처 설계 · 개발 · QA · 문서화 (1인, PM+개발 겸임)
- **기간**: 2026-07-29 ~ 2026-08-06 (9일, 커밋 49건)
- **팀 구성**: 1인 (설계상으로는 24명 AI 에이전트·8부서 조직을 시스템 내부에 구현)
- **한 줄 임팩트**: "에이전트가 완료했다고 말하면 믿는다" 구조를 "실제 파일·검증 명령·독립 리뷰 3중 증거 없이는 완료 아님" 구조로 뒤집어, 멀티 에이전트 시스템의 신뢰 문제를 아키텍처 레벨에서 해결

---

## Problem

LLM 멀티 에이전트 시스템 대부분은 두 가지 중 하나에서 멈춘다.

1. **채팅 역할극**: 에이전트끼리 대화만 주고받고 실제 파일 변경은 없음.
2. **에이전트 자기 보고 신뢰**: 모델이 "완료했습니다"라고 말하면 그대로 완료 처리. 실제로는 파일이 안 바뀌었거나 검증을 안 거친 상태.

이 프로젝트가 풀려던 문제는 두 번째다. 24명 규모 AI 조직을 시스템으로 구현하려면 다음 제약이 동시에 걸린다.

- **신뢰 문제**: 모델 출력을 그대로 "완료" 판정에 쓸 수 없다. 증거가 필요하다.
- **권한 문제**: 에이전트에게 파일 쓰기·명령 실행 권한을 얼마나, 어떤 범위로 줄지 정해야 한다. 너무 넓으면 위험, 너무 좁으면 무용지물.
- **장애 복구 문제**: worker 프로세스가 죽어도 Job이 "영원히 실행 중"으로 남으면 안 된다.
- **조직 설계 문제**: 24명·8부서 규모에서 하드코딩된 라우팅 표는 유지보수가 불가능하다. 하지만 완전 자율 배정은 예측 불가능하다.

**목표**: "실행이 실제로 안전하고, 완료 판정이 실제로 정확한" 멀티 에이전트 실행 시스템을 로컬 환경에서 동작하게 만드는 것. 범위는 의도적으로 좁혔다. 멀티테넌트, 자동 배포, 무제한 자율 실행은 비목표(non-goal)로 명시.

## Process

### 우선순위 결정

가장 먼저 정한 건 "무엇을 안 만들 것인가"였다. README에 비목표를 명시적으로 박아둔 이유는, 데모용 멀티 에이전트 프로젝트가 흔히 빠지는 함정(멀티테넌트로 확장하려다 핵심 신뢰 문제를 미루는 것)을 피하기 위함이다.

핵심 설계 결정 순서:
1. **Task/Job 상태 분리** 먼저 확정. 사용자가 이해하는 단계(Task)와 실행기 내부 상태(Job)를 섞으면 이후 모든 기능(재시도, 복구, UI 표시)이 꼬인다는 걸 초기에 판단.
2. **증거 게이트**를 다른 기능보다 먼저 설계. 파일 hash, 검증 명령 종료 코드, 독립 리뷰 통과 3가지를 완료 조건으로 못 박음. 이후 모든 기능은 이 게이트를 우회하지 않는지가 리뷰 기준이 됨.
3. **권한 모델(TaskContract)**. 요청 단위로 allow/ask/deny 규칙 발급. `ask` 등급은 HTTP 428로 멈추고 사용자 승인 대기하도록 해서, "권한 있음/없음" 이분법이 아닌 3단계 모델 채택.
4. **동적 라우팅**. 정적 매핑 표 대신, 매 요청마다 모델이 부서 경계 정의 + 가용 인력·스킬을 함께 보고 배정하도록 함. `registry/task-profiles.json`을 의도적으로 비워둬서 "하드코딩 라우팅 없음"을 코드 레벨에서 강제.

### 트레이드오프 결정

- **자율성 vs 안전성**: 목표는 "대화만으로 접수→계획→실행→검증까지" 가는 대화형 자율 실행이지만, 파괴적·외부 전송·비용·배포 행동은 자율성 레벨과 무관하게 항상 명시 승인을 유지하기로 결정. 속도보다 되돌릴 수 없는 행동의 통제를 우선.
- **정적 라우팅 vs 동적 라우팅**: 정적 라우팅이 더 빠르고 예측 가능하지만, 24명·8부서 규모에서는 유지보수 비용이 기하급수적으로 늘어난다고 판단해 동적 라우팅을 채택. 대신 `verify_routing.py`로 정합성을 계속 검사하는 방식으로 예측 불가능성을 상쇄.
- **단일 프로세스 vs 다중 worker**: 단일 프로세스가 디버깅은 쉽지만, 회의·실행이 동시에 여러 건 돌아야 하는 조직 시뮬레이션 특성상 다중 worker + SQLite WAL 조합을 선택. 대신 lease/heartbeat로 죽은 worker 감지 비용을 지불.

## Solution

**구현한 것**:
- FastAPI 기반 API + 다중 worker 프로세스 + SQLite(WAL) 실행 엔진 (`apps/api`, 약 8,400줄)
- React/Vite/TS 관제 UI, SSE로 회의 발언·도구 호출·파일 변경·검증 결과 실시간 스트리밍 (`apps/web`, 약 1,250줄)
- 24명 페르소나 + 8부서 경계 정의 + 부서별 스킬 풀 (`employees/`, `registry/`, `skills/`)
- TaskContract 기반 3단계 권한 모델(allow/ask/deny), HTTP 428 승인 플로우
- 증거 게이트: 파일 hash + 검증 명령 + 독립 리뷰(GUARD/LENS) 3중 확인 후에만 `completed` 전이
- 체크포인트 복원, lease 만료 시 자동 `interrupted` 처리, 재시도 시 이미 성공한 단계 스킵
- API/worker 버전 불일치 하드 차단 (`/api/runtime/version`)

## Learnings

**잘된 점**
- 완료 판정을 "증거 3종" 조건으로 초기에 못 박은 게, 이후 기능을 추가할 때마다 "이게 게이트를 우회하지 않는가"를 자동으로 리뷰 기준으로 만들어줬다. 실제로 트러블슈팅 사례 대부분이 이 게이트 관련 회귀였고, 기준이 명확했기 때문에 빠르게 잡을 수 있었다.
- 비목표를 README에 먼저 박아둔 게 스코프 크리프를 막는 데 효과적이었다. 9일이라는 짧은 기간에 "로컬·단일 사용자"로 좁힌 덕분에 핵심 신뢰 문제에 집중할 수 있었다.

**아쉬운 점 / 다음에 다르게 할 것**
- E2E 테스트에 bare `return`이 들어가 절반이 무력화된 채로 여러 커밋을 통과한 사례(`07c73e8`)는, "테스트 통과"와 "assertion이 실제로 실행됨"을 구분하는 별도 점검(예: mutation testing, coverage 라인별 확인)을 더 일찍 넣었어야 했다는 교훈으로 남았다.
- 게이트 로직과 그 로직이 참조하는 설정 파일(`department-boundaries.json`)을 분리 커밋하다 보니 "코드는 있는데 설정이 없어 무력화" 상태가 HEAD에 남은 적이 있다(`61413ea`). 로직·설정을 같은 커밋에 묶거나, 설정 필드 존재 여부를 CI에서 강제하는 걸 더 앞단에 뒀어야 했다.
- 1인 개발이라 "다른 시각의 리뷰"가 구조적으로 없었다. 시스템 안에 GUARD(독립 시험)·LENS(여정 검토) 역할을 설계해 넣은 것 자체가, 개발 과정에서 겪은 "혼자서는 자기 실수를 못 본다"는 문제의식을 반영한 결과이기도 하다.
