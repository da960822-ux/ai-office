# 회고: AI Office (Corporate OS v6.2)

기간: 2026-07-29 ~ 2026-08-06 (9일). 1인 개발.

## 좋았던 점

- **원칙을 코드보다 먼저 정한 것.** "증거 없으면 완료 없음"을 문서와 게이트 로직 양쪽에 먼저 박아두고 시작하니, 이후 어떤 기능을 추가하든 "이게 이 원칙을 어기는가"라는 단일 기준으로 판단할 수 있었다. 원칙이 늦게 나오면 나중에 있는 기능들을 다 되짚어야 하는데 그 비용을 피했다.
- **비목표를 먼저 선언한 것.** 멀티테넌트, 자동 배포, 무제한 자율 실행을 README에 "안 한다"고 못 박아두니, 9일이라는 짧은 기간에도 스코프가 안 늘어났다. 확장하고 싶은 유혹이 여러 번 있었는데(특히 자율 실행 관련) 문서에 적어둔 비목표가 제동 역할을 했다.
- **정적 정합성 검사 스크립트를 3개나 자체 구축한 것.** `verify_routing.py`, `verify_skills.py`, `audit_package.py`. 24명·8부서 규모에서 사람이 눈으로 체크하면 반드시 놓치는 것들(설정 필드 누락, 스킬 lock 불일치, YAML 파싱 오류)을 기계적으로 잡아내는 안전망을 만든 게, 실제로 트러블슈팅 사례 중 여러 건을 조기에 발견하는 데 직접 기여했다.

## 힘들었던 점

- **혼자서 리뷰어 역할까지 겸임.** 시스템 설계에는 GUARD(독립 시험)·LENS(여정 검토)라는 "제3자 리뷰" 역할을 넣어놓고, 정작 이 시스템을 만드는 나 자신에게는 그런 리뷰가 없었다. E2E 테스트에 bare `return`이 들어간 채로 여러 커밋 동안 안 잡힌 것도, 결국 "내가 짠 테스트를 내가 통과시켰다고 믿는" 함정에서 나온 문제였다.
- **크로스플랫폼 이슈는 예상보다 늦게 터졌다.** Windows에서 스킬 해시 102개 중 98개가 깨진 사건은, macOS/Linux 개발 중에는 전혀 안 보이다가 fresh clone 시점에야 드러났다. 플랫폼 차이는 "코드 리뷰"로는 못 잡고 실제 다른 환경에서 돌려봐야만 잡힌다는 걸 다시 확인했다.
- **정상 경로만 테스트하고 예외/fallback 경로를 놓치는 패턴이 반복됐다.** 부서 스테이지 게이트가 fallback plan 경로에서는 빠져 있던 사례(`9ef703a`)가 대표적. 게이트를 넣을 때 "이 게이트를 우회할 수 있는 다른 코드 경로가 있는가"를 체크리스트화하지 않은 게 원인이었다.

## 배운 것 (기술·프로세스)

- **신뢰 가능한 자동화의 핵심은 "완료 판정 기준"이다.** LLM 에이전트 오케스트레이션에서 진짜 어려운 문제는 모델 호출이 아니라, "언제 끝났다고 믿을 것인가"를 시스템 레벨에서 강제하는 것이었다.
- **조용한 실패(silent failure)는 명시적 실패보다 훨씬 위험하다.** 이번 프로젝트에서 발견·수정한 문제 6건 중 대다수가 "에러가 안 났는데 실제로는 틀렸다"는 유형이었다(파싱 실패 무기록, 게이트 무력화, 무력화된 테스트). 에러를 던지는 코드보다 조용히 넘어가는 코드를 더 의심해야 한다는 걸 체감했다.
- **설정 파일과 그 설정을 참조하는 로직은 분리해서 리뷰하면 위험하다.** 로직 커밋과 설정 커밋이 따로 나가면 "코드는 배포됐지만 설정이 안 됨" 상태가 눈에 안 띄게 HEAD에 남을 수 있다.

## 다음에 하고 싶은 것 (로드맵 연장선)

- **제품 파이프라인 계층 구현**: 지금은 실행 계층(Task/Job/증거 게이트)까지 구현됐고, 제품 계층(Blueprint, 산출물 버전, handoff 계약, 준비도 판정, Export)은 미구현. `reference/legacy/VIBEOFFICE_GAP_ANALYSIS.md`에 격차를 기록해둠.
- **대화형 자율 실행**: 지금은 팀장·실행자를 사용자가 단계별 버튼으로 진행하는데, 목표는 자연어 한 문장으로 접수→계획→실행→검증→보고까지 시스템이 스스로 진행하고 사람은 대화로만 개입하는 것. 단, 파괴적·외부 전송·비용·배포 행동의 명시 승인은 자율성 레벨과 무관하게 유지.
- **mutation testing 또는 라인 커버리지 확인 도구 도입**: E2E 테스트 무력화 사례를 겪은 후, "테스트 통과"와 "assertion이 실제로 실행됨"을 구분하는 자동 점검을 CI에 넣고 싶다.
