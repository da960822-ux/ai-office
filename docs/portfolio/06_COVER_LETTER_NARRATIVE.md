# 자기소개서 서사 초안: IT PM 지원용

특정 회사·공고 정보가 없어 범용 템플릿으로 작성했다. `[회사명]`, `[직무]`, `[지원 동기가 될 회사 특성]` 부분은 실제 지원 공고에 맞춰 채워 넣어야 한다. 이 문서 자체를 그대로 제출하지 말고, 지원할 공고를 알려주면 해당 회사 요구사항에 맞춰 다시 다듬는 걸 권한다.

---

## 지원 동기 (Opening Hook)

[회사명]의 [지원 동기가 될 회사 특성. 예: 특정 제품, 기술 스택, 조직 문화]에 관심을 갖게 된 계기는, 최근 진행한 개인 프로젝트에서 겪은 문제와 맞닿아 있다. 에이전트 여러 명이 동시에 파일을 수정하는 멀티 에이전트 시스템을 설계하면서, "작업을 완료했다"는 보고를 어떻게 검증할 것인가라는 문제에 부딪혔다. [직무]로서 이 경험을 [회사명]의 [관련 업무]에 적용하고 싶어 지원한다.

## 직접 매칭 경험 (Body 1)

9일간 24명 규모의 AI 에이전트 조직을 시스템으로 구현하면서, 완료 판정을 "파일 hash·검증 명령 종료 코드·독립 리뷰 통과" 3중 조건으로 설계했다. 이 원칙을 먼저 정해두니, 이후 어떤 기능을 추가하든 "이게 이 원칙을 우회하는가"라는 단일 기준으로 검토할 수 있었다. 실제로 이 기준 덕분에 개발 기간 중 조용한 실패 유형의 버그 6건(설정 파일 누락으로 무력화된 게이트, fallback 경로의 게이트 우회, 무력화된 E2E 테스트 등)을 직접 발견하고 수정했다. 문제를 코드로만 풀지 않고 "무엇을 원칙으로 먼저 정할 것인가"부터 결정하는 방식이, PM으로서 내가 일하는 순서다.

## 추가 역량 (Body 2)

혼자 개발하면서 가장 크게 느낀 한계는 "다른 시각의 리뷰가 구조적으로 없다"는 점이었다. 그래서 시스템 안에도 독립 시험(QA)과 여정 검토(문서화) 역할을 분리해서 넣었다. 이 경험을 통해, 좋은 프로세스는 사람이 실수하지 않기를 기대하는 게 아니라 실수가 나도 걸러지는 구조를 만드는 것이라는 걸 실감했다. [직무] 역할에서도 기능 하나를 만드는 것보다, 그 기능이 틀렸을 때 어떻게 걸러지는지를 먼저 설계하는 방식으로 일하고 싶다.

## 마무리 (Closing)

멀티테넌트 확장이나 자동 배포 같은 화려한 기능보다, 로컬 환경에서 "에이전트가 실제로 안전하게 파일을 건드리게 만드는" 좁고 확실한 문제에 9일을 집중했다. [회사명]에서도 이런 방식으로, 화려함보다 실제로 작동하는 것을 우선하는 태도로 기여하고 싶다.
