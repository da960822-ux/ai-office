# VibeOffice S2: 기획→디자인 인계 계약과 Design Package 생성

S1이 만든 승인된 blueprint를 입력으로 `vo_handoffs` 봉투를 만들고, 그 봉투가 승인되면 디자인 부서가 5종 마크다운(IA·USER_FLOWS·SCREEN_SPEC·DESIGN_SYSTEM·COMPONENT_INVENTORY)을 결정론적으로 생성해 버전 관리한다. 승인 경계는 `blueprint.approved_blueprint_for_handoff` 하나로 좁혀져 있고, 05A §3 거부 조건 5개는 코드로 실행되며, Gate C는 파일을 쓰기 전에 in-memory 패키지에 대해 돈다. 상태 머신은 S1 테이블을 남긴 채 S2 테이블을 union하는 방식으로 확장했고, blueprint 개정은 stale 전파 + handoff superseded로 이어진다. 테스트 30건 전부 통과(`unittest apps.api.test_vibeoffice_handoff`, 12.6s).

**Watch for:**
- **한 DB에 두 번째 프로젝트가 인계를 만들면 500이 난다** (confirmed, blocker). `vo_handoffs.id`는 전역 PK인데 ID 생성은 프로젝트별 시퀀스라 `HO-PLN-DES-001`이 충돌하고 `sqlite3.IntegrityError`가 그대로 올라온다. 테스트가 매 케이스마다 새 임시 DB를 쓰기 때문에 구조적으로 가려져 있다.
- **`revise_blueprint`가 상태 전이를 마지막에 검증해서 파일/DB가 갈라진다** (confirmed, high). 미승인(`PLANNING_REVIEW`) 상태에서 호출하면 blueprint 파일은 새 본문으로 덮인 뒤 예외가 나고 DB는 롤백된다. 이후 sha256이 어긋나 승인 게이트가 계속 409를 낸다.
- **Gate C는 API 경로에서 절대 실패할 수 없다** (confirmed, high). 생성기가 항상 게이트를 만족하도록 만들어져 있어, 게이트는 단위 테스트에서만 살아 있고 파이프라인에서는 죽은 코드다. 09A Gate C 위반 시 "Design 반송"이라는 규칙에 대응하는 실행 경로가 없다.
- **거부 조건 5개 중 1개는 API에서 도달 불가, 2개는 정상 입력을 오차단한다** (confirmed, high). "1인 카페 사장" 같은 단일 페르소나가 페르소나 충돌로 거부된다.
- **stale 전파가 명세보다 좁고, 변경 분류가 실제 렌더링 의존성을 반영하지 않는다** (confirmed, medium).
- **`revise_blueprint`에는 라우트가 없다** (confirmed, medium). stale 전파와 supersede 전체가 API로는 도달 불가하다.

## High-level view

승인 경계 설계는 이 슬라이스에서 가장 잘 된 부분이고 되돌리면 안 되는 부분이다. 다음 부서가 blueprint를 읽는 문은 `approved_blueprint_for_handoff` 하나뿐이고, 그 함수가 프로젝트 상태·승인 시각·스키마·Gate B·디스크 해시를 전부 다시 확인한다. S2 어느 모듈도 handoff 목적으로 `vo_blueprints.content_json`을 직접 읽지 않는다(`revise_blueprint`가 직전 본문을 읽지만 diff 용도이고 재검증을 거친다). 미승인 draft가 부서 선을 넘는 경로는 찾지 못했다.

봉투 내용이 상수 배열이 아니라 blueprint에서 파생되고, 테스트가 프로젝트별로 그 값이 실제로 달라지는지 확인한다는 점도 지켜야 한다. 고정 배열이면 봉투가 "그럴듯하지만 이 프로젝트에 대해 아무 말도 하지 않는" 문서가 됐을 것이다.

Gate C는 코드로 존재하고 단위 테스트로 살아 있지만 파이프라인에서 load-bearing이 아니다. 생성기가 화면 수·Must 연결·CTA·3상태·반응형·접근성을 모두 항상 만족시키도록 만들어져 있어, 실제 입력으로 게이트가 발동할 조합이 없다.

거부 조건 5개는 실행되긴 하지만 품질이 고르지 않다. Must 5개 초과 조건은 상위 Gate B가 먼저 막으므로 API에서 도달 불가하고, 페르소나 충돌과 성공 장면 조건은 정상적인 한국어 입력을 오차단한다. 미결정 사항 조건은 S1이 실제로 쓰는 문자열과 정확히 맞물려 있어 도달 가능하지만, 문자열 리터럴이 두 모듈에 중복되어 있다.

stale 전파는 "최소 영향 수정"을 데이터로 표현했다는 점에서 방향이 옳고, 집합이 서로 다르다는 것을 테스트가 지킨다. 다만 실제 렌더러 의존성과 어긋난다: `INFORMATION_ARCHITECTURE.md`는 Must id와 `oneLineDefinition`을 본문에 담는데 Must 변경·문구 변경 모두 IA를 stale로 표시하지 않는다. 변경 분류도 `(id, name)`만 보므로 `userValue` 수정은 어떤 종류로도 분류되지 않고 조용히 지나간다.

superseded 체인은 순환하지 않고 끊기지도 않지만(항상 더 오래된 행을 가리킨다) 05A §10과 트리거가 다르다. 명세는 "승인 후 입력 산출물이 바뀌면"인데 구현은 입력이 그대로여도 `POST /handoffs` 재호출로 앞의 봉투를 superseded로 만든다. 더 실질적인 위험은 디스크에 `planning-to-design.json` 하나뿐이라는 점이다 — 가이드 §5는 `handoffs/*.json`을 명시하고, 개정으로 supersede가 일어난 직후 그 파일에는 후속 봉투 없이 `superseded` 상태의 죽은 계약이 남는다.

상태 머신 union은 실제로는 `PLANNING_APPROVED` 한 곳만 넓혔고 그건 의도된 것이다. 문제는 가드 테스트가 `S1_TRANSITIONS[state] <= TRANSITIONS[state]`를 검사한다는 것 — 이 방향의 포함 관계는 union의 정의상 항상 참이라 "S1이 금지한 전이가 여전히 금지된다"를 증명하지 않는다. 그리고 `require_s1_transition`은 프로덕션 호출자가 사라졌다. S1이 갖고 있던 "기획 코드는 기획 상태 밖에서 돌 수 없다"는 가드가 함께 사라졌고, 그 결과 `blueprint/generate`가 `STALE_ARTIFACTS`에서 호출되어 v2 본문을 같은 버전 번호로 제자리 덮어쓸 수 있다.

파일과 DB 정합성은 `database()`가 예외 시 커밋하지 않는 구조(main.py:341-351)에 의존한다. DB는 롤백되지만 이미 쓰인 파일은 남는다. `record_artifact`는 파일 쓰기와 두 INSERT 사이에 검증이 없어 창이 좁지만, `revise_blueprint`는 파일 쓰기와 상태 검증 사이에 넓은 창이 있고 그 창이 실제로 열린다.

## Handoff ID가 프로젝트별로 매겨지는데 PK는 전역

`schema.py:391-392`는 `vo_handoffs.id`를 `TEXT PRIMARY KEY`로 선언한다. `handoff.py:318-329`의 `_next_handoff_id`는 시퀀스를 `SELECT COUNT(*) FROM vo_handoffs WHERE project_id = ?`로 구하고, 충돌 확인 루프도 `WHERE project_id = ? AND id = ?`로 프로젝트 안에서만 본다. 결과적으로 서로 다른 프로젝트가 모두 `HO-PLN-DES-001`을 요구한다.

같은 DB에서 두 프로젝트를 승인한 뒤 각각 인계를 만든 결과:

```text
project1 handoff: 201 HO-PLN-DES-001
project2 handoff RAISED: IntegrityError UNIQUE constraint failed: vo_handoffs.id
```

`routes.post_handoff`는 `IntegrityError`를 매핑하지 않으므로 500이다. 실 서비스 DB는 하나이므로 두 번째 프로젝트부터 인계가 불가능하다.

테스트가 이걸 못 잡는 이유가 구조적이라는 점이 더 중요하다. `setUp`이 케이스마다 새 임시 DB를 만들고, 한 케이스 안에서 두 프로젝트를 만드는 유일한 테스트(`test_a_clean_blueprint_is_not_rejected`)는 인계를 만들지 않는다. 프로젝트 간 ID 격리를 확인하는 테스트가 없다.

## 파일은 써지고 DB는 롤백되는 창

`artifacts.revise_blueprint`의 순서: 스코프 게이트 → 스키마 검증 → **blueprint 파일 쓰기**(artifacts.py:404-406) → INSERT → stale 표시 → supersede → `set_project_state(STALE_ARTIFACTS)`(artifacts.py:426). 마지막 전이가 상태에 따라 실패한다. `TRANSITIONS[PLANNING_REVIEW]`에는 `STALE_ARTIFACTS`가 없다.

`PLANNING_REVIEW`(생성 직후, 아직 승인 전) 상태에서 호출한 결과:

```text
state: PLANNING_REVIEW
revise raised: StateTransitionError 현재 상태 PLANNING_REVIEW에서 STALE_ARTIFACTS(으)로 넘어갈 수 없습니다.
db rows: [(1, '68677fd3')]          # v2 행 없음 — 롤백됨
disk sha: 76ff3c49  name: 새 이름     # 디스크는 새 본문
approve: 200
handoff: 409 Blueprint 파일이 승인 이후 변경되었습니다. 다시 생성하고 승인해야 합니다.
```

승인 게이트가 파일 해시를 다시 확인하기 때문에 divergence를 **감지**하는 건 잘 된 설계다. 하지만 이 프로젝트는 승인을 통과해도 인계를 만들 수 없는 상태에 갇힌다. `blueprint/generate`를 다시 돌리면(PLANNING_REVIEW → PLANNING_REVIEW 허용) 파일과 DB가 다시 맞춰져 복구는 되지만, 사용자가 손으로 고친 본문은 사라진다.

`HANDOFF_REJECTED`에서도 같은 일이 일어난다. 그 상태의 출구는 `{PLANNING, PLANNING_REVIEW}`뿐이라 `STALE_ARTIFACTS`로 못 간다. 즉 "거부된 인계를 고치려고 blueprint를 개정한다"는 가장 자연스러운 시나리오가 정확히 이 함정을 밟는다.

blueprint v1과 v2가 같은 경로(`.vibeoffice/project-blueprint.json`)를 공유하므로 개정 성공 후에도 v1 행의 sha256은 영구히 검증 불가다:

```text
v1 recorded: 68677fd3  v2 recorded: c5f3b916  disk now: c5f3b916  same path: True
```

`vo_artifact_versions`도 같은 성질을 갖는다 — `_write_doc`이 `ARTIFACT_FILENAMES[type]` 고정 이름을 쓰므로 이력은 DB에만 있고 워크스페이스에는 최신본만 있다. `history` 배열의 sha256은 최신 버전에 대해서만 확인 가능한 값이다.

## Gate C가 무엇을 지키고 무엇을 지키지 않는가

`assert_gate_c`(design.py:398-448)는 09A Gate C(57~64행)의 항목을 충실히 옮겼고, 위반을 하나씩 모아 한 번에 돌려준다. `build_design_package`가 게이트 통과 후에만 반환하고 `run_design`이 DB 트랜잭션 **전에** 그것을 호출하므로, 게이트 실패 시 워크스페이스가 깨끗하게 남는다.

문제는 생성기가 게이트를 만족하도록 설계되어 있다는 점이다:

- 화면 수 = `1 + min(len(must), 6)`. Gate B가 Must를 3~5로 묶으므로 항상 4~6. 상한·하한 모두 걸리지 않는다.
- 넘치는 Must는 마지막 화면에 얹혀서(design.py:227-231) "모든 Must가 화면에 연결"이 문자 그대로 항상 참이 된다.
- 흐름은 Must마다 하나씩 만들어지므로 `flow_features`가 항상 Must 전체를 덮는다.
- `next_screens`는 진입 화면은 기능 화면들, 기능 화면은 항상 `(SCR-001,)`. dead-end 불가.
- `cta_label`/`cta_action`은 `_KIND_CTA[kind]`에서, `responsive`/`accessibility`는 하드코딩 문자열에서 온다. 비어 있을 수 없다.
- `_states_for`가 `_DATA_DRIVEN_KINDS`에 대해 항상 3상태를 채우고, `data_driven` 플래그도 같은 집합에서 계산된다. 두 값이 같은 출처라 불일치가 불가능하다.

Must 3·4·5개로 직접 확인한 결과 전부 통과(화면 4·5·6개)했고, Gate B가 유효한 blueprint로 게이트를 실패시키는 조합을 찾지 못했다.

`assert_gate_c` 본문을 `return`으로 바꾸면 실패하는 테스트는 4건 있다(`test_gate_c_blocks_an_unlinked_must_feature`, `..._a_dead_end_screen`, `..._a_data_screen_without_three_states`, `..._a_screen_count_outside_three_to_seven`). 즉 **함수는 확실히 load-bearing**이다. 하지만 네 건 모두 생성된 패키지를 `dataclasses.replace`로 손으로 망가뜨린다. 게이트가 실제 파이프라인에서 무언가를 막는다는 증거는 없다.

결정론적 생성기 + 코드 게이트라는 조합에서 게이트가 회귀 감지기 역할을 하는 것 자체는 타당하다. 다만 두 가지가 비어 있다. 첫째, 09A/가이드 §8의 "Gate C 위반 → Design 반송"에 해당하는 실행 경로가 없다. `GateCError`는 422로 끝나고 프로젝트 상태는 `PLANNING_APPROVED`에 그대로 남는다. 둘째, `HandoffStatus.CHANGES_REQUESTED`는 상태 머신에 있지만 어떤 코드도 그 상태로 전이시키지 않는다. S5의 QA 반송 루프가 이 두 구멍을 메워야 한다.

## 거부 조건 5개의 실제 동작

**조건 1 (Must 5개 초과 + 근거 없음)** — API에서 도달 불가. `create_handoff`는 `approved_blueprint_for_handoff`를 먼저 호출하고, 그 함수가 `assert_scope_gate`를 다시 돌린다. Must가 6개인 blueprint는 `ScopeGateError` → 409에서 끝나고 `evaluate_rejection_reasons`까지 오지 않는다. 테스트도 순수 함수만 호출한다. `MIN_RATIONALE_CHARS = 8`로 스키마의 `minLength: 1`을 보강한 발상은 좋지만, 그 코드가 실행되는 경로가 없다.

**조건 2 (대상 사용자 충돌)** — 도달 가능하지만 오차단한다. `_persona_groups`(handoff.py:146-153)가 페르소나 문자열마다 모든 그룹 키워드를 검사하고 결과를 하나의 집합에 누적한다. 한 문자열이 두 그룹에 걸리면 페르소나가 하나여도 충돌로 판정된다:

```text
targetUsers=["1인 카페 사장"]      → 거부: "대상 사용자가 서로 충돌합니다: 개인 사용자, 조직 구성원"
targetUsers=["개인 병원 담당자"]   → 거부: 같은 이유
targetUsers=["동네 카페 사장"]     → 통과
```

`1인`/`개인`(개인 사용자)과 `사장`/`담당자`(조직 구성원)가 동시에 걸린다. "1인 카페 사장"은 이 제품의 대표 사용자 서술에 가깝다. 판정을 페르소나 단위로 내리고, 서로 다른 페르소나가 서로 다른 그룹일 때만 충돌로 봐야 한다.

빈 `targetUsers` 검사는 별개로 두었는데, 스키마가 `minItems: 1`을 요구하므로 이것도 API에서는 도달 불가하다.

**조건 3 (성공 장면이 화면 행동으로 안 바뀜)** — 도달 가능하지만 오차단한다. `OBSERVABLE_ACTION_MARKERS`가 활용형을 못 잡는다:

```text
"재고가 부족하면 알림을 받고 바로 주문한다"  → 거부
"매일 아침 부족한 재고를 한눈에 확인한다"    → 통과
```

마커에 `받는`·`받아`는 있지만 `받고`는 없고, `주문`은 아예 없다. S1 생성기가 만드는 문장은 통과하겠지만(테스트 2건이 확인), 사용자가 직접 답한 성공 장면은 임의의 한국어다. 조건 3은 사용자 입력에 가장 많이 노출되는데 마커 방식이 가장 취약하다.

**조건 4 (Out 기능이 Must/Should에 재등장)** — 도달 가능하고 실제 API 경로에서 테스트된다. 명세 원문은 "Out 기능이 Requirements에 포함"인데 REQUIREMENTS.md가 아직 없어 Must/Should를 대신 본다. 지금으로선 합리적인 대체지만 주석에 그 사실이 없다. id가 아니라 이름으로 비교하는 것은 맞는 선택이다 — S1 생성기가 Out과 Must에 같은 이름을 다른 id로 쓸 수 있다.

**조건 5 (미결정 사항이 화면 구조를 바꿈)** — 도달 가능하고, S1이 실제로 쓰는 문자열과 정확히 맞물린다. `blueprint._open_questions`(blueprint.py:240-253)가 `f"{label} - {text} (사용자가 '나중에 결정'을 선택함)"`을 쓰고, `intake.FIELD_LABELS`의 값이 `프로젝트 종류`/`대상 사용자`/`로그인·인증`/`데이터 저장`/`AI 기능`이다. `STRUCTURAL_DECISION_LABELS`의 다섯 문자열과 정확히 일치한다.

두 가지 주의점. 첫째, 이 일치가 문자열 리터럴 중복으로 유지된다 — `intake.FIELD_LABELS`에서 라벨 하나만 다듬으면 조건 5가 조용히 죽는다. 둘째, `STATUS_ASKED`(답변 없이 추천값으로 진행) 분기는 `나중에 결정`을 포함하지 않으므로 조건 5를 발동시키지 않는다. 추천값이 적용된 것이니 이 구분은 맞다고 본다 — 그리고 그 항목은 `openDecisions`로 여전히 디자인 부서에 전달된다.

`test_a_clean_blueprint_is_not_rejected`가 오차단 가드를 두었다는 것 자체는 지켜야 할 선택이지만, 커버하는 입력이 S1 생성기가 만든 것 2건뿐이어서 위의 두 오차단을 잡지 못했다.

## stale 전파와 변경 분류

`STALE_IMPACT`(artifacts.py:112-126)는 가이드 §9의 네 가지 케이스를 모두 키로 갖고, 집합이 서로 다르다는 것을 `test_stale_impact_differs_by_kind_of_change`가 지킨다 — "전부 stale로 표시"하는 안전하지만 무의미한 구현으로 되돌리지 못하게 막는 장치라 보존해야 한다.

렌더러가 실제로 무엇을 읽는지와 맞춰 보면 누락이 드러난다:

```text
render_information_architecture  ← targetUsers, oneLineDefinition, screen.features(Must id), screen.route
render_user_flows                ← screens, flows
render_screen_spec               ← 전 필드 (kind, data source, states, CTA)
render_design_system             ← targetUsers, successMoment, skillLevel
render_component_inventory       ← screen.components (kind에서 파생)
```

- `CHANGE_MUST` → IA 누락. IA는 "화면과 Must 기능 연결" 표와 화면 트리를 담고, 화면 id는 Must 순서에 따라 위치로 결정된다.
- `CHANGE_VISUAL` → IA 누락. `_VISUAL_FIELDS`에 `oneLineDefinition`이 있고 IA 본문 두 번째 줄이 그 값이다.
- `CHANGE_VISUAL` → DESIGN_SYSTEM은 포함되어 있지만, DESIGN_SYSTEM이 읽는 것은 `targetUsers`/`successMoment`/`skillLevel`이고 `_VISUAL_FIELDS`에는 그 중 아무것도 없다. 문구 변경으로 DESIGN_SYSTEM을 표시하는 건 과잉이고, `successMoment` 변경은 어떤 종류로도 분류되지 않아 DESIGN_SYSTEM이 실제로 낡을 때는 표시되지 않는다.
- `CHANGE_TECH_STACK` → SCREEN_SPEC 누락. `dataPersistence`가 진입 화면의 kind와 모든 화면의 `data` 문장을 결정한다(design.py:106-114, 254-256).

`classify_blueprint_change`의 오분류:

- `_feature_signature`가 `(id, name)`만 본다. `userValue` 수정은 SCREEN_SPEC의 `purpose`를 바꾸지만 어떤 변경 종류도 발생하지 않는다 → `mark_stale`이 빈 목록을 반환하고 산출물은 표시 없이 낡는다.
- `should`/`later`/`out` 변경은 전혀 분류되지 않는다. Out 추가는 봉투 `constraints`를 바꾸고 거부 조건 4를 새로 위반할 수도 있다.
- `successMoment`·`coreProblem`·`constraints.skillLevel`·`constraints.deadline` 변경도 분류 대상이 아니다. `skillLevel`은 DESIGN_SYSTEM 본문의 초보자 언어 항목과 봉투 constraints를 바꾼다.
- Must 순서 변경은 리스트 비교라 정상적으로 감지된다. 화면 id가 위치 기반이므로 이건 감지되어야 맞다.

반대 방향(과잉)은 `_VISUAL_FIELDS`의 `projectName` 정도다. SCREEN_SPEC은 `projectName`을 렌더링하지 않는데 이름만 바꿔도 stale이 된다. 영향은 작다.

## superseded 체인과 디스크 이력

`create_handoff`(handoff.py:490-495)는 상태와 무관하게 `created_at DESC, id DESC` 첫 행을 `supersedes`로 잡는다. 체인이 순환할 수는 없다 — 항상 자신보다 먼저 만들어진 행을 가리키고, 새 행은 아직 존재하지 않는다. 삭제 경로가 없으므로 끊길 수도 없다.

트리거가 05A §10과 다르다. 명세는 "승인 후 입력 산출물이 바뀌면 기존 handoff는 superseded"다. 구현은 입력이 그대로여도 재호출로 supersede한다:

```text
h1 HO-PLN-DES-001 ready_for_review sup=None
h2 HO-PLN-DES-002 ready_for_review sup=HO-PLN-DES-001
statuses: {HO-PLN-DES-001: superseded, HO-PLN-DES-002: ready_for_review}
```

두 봉투의 `inputVersions`가 동일하다. "대체"라는 단어가 서로 다른 두 사건(입력 변경 / 단순 재생성)을 덮는다. 입력 버전이 같으면 기존 live 봉투를 반환하는 편이 계약에 가깝다.

05A §10의 "모든 리인계는 변경 diff와 이유를 포함"은 구현되지 않았다. 후속 봉투에는 `supersedes` id만 있고, 사유는 **선행** 봉투의 `rejection_reasons_json`에 들어간다(`"HO-...-002이(가) 이 인계를 대체했습니다."`) — 이유가 대체된 쪽에 기록되고 대체하는 쪽에는 없다. 그 컬럼을 supersede 사유에 재사용한 것도 의미 혼동을 만든다: 거부 사유와 대체 사유가 같은 필드에서 나온다.

디스크 이력이 가장 실질적인 위험이다. `PLANNING_TO_DESIGN_FILENAME`은 고정 상수고 `set_handoff_status`가 상태가 바뀔 때마다 그 파일을 다시 쓴다. 개정으로 supersede가 일어난 직후:

```text
envelope on disk: HO-PLN-DES-002  status=superseded
files in handoffs/: ['planning-to-design.json']
```

워크스페이스에는 후속 봉투 없이 죽은 계약만 남는다. `supersede_live_handoffs`가 여러 live 봉투를 처리하면 마지막으로 처리된 것이 파일을 차지한다. 가이드 §5의 워크스페이스 배치는 `handoffs/*.json`(복수)이고 이 폴더는 그대로 내보내진다. Codex·Claude가 이어받을 때 보게 되는 것이 `superseded` 봉투 하나라면 05A §1("승인된 버전만 사용")을 파일 수준에서 지킬 수 없다.

## 다음 슬라이스가 걸릴 지점

**S3 (기술설계)의 입력 게이트.** `approved_blueprint_for_handoff`는 프로젝트 상태가 정확히 `PLANNING_APPROVED`일 것을 요구한다(blueprint.py:709-713). `run_design`이 끝나면 프로젝트는 `DESIGN_REVIEW`다:

```text
rerun design after revision: 409 기획 승인 전에는 다음 부서로 넘길 수 없습니다.
                                 현재 상태: PLANNING_REVIEW (필요 상태: PLANNING_APPROVED)
```

즉 디자인 이후 어떤 부서도 blueprint를 읽을 수 없다. S3는 (a) 이 게이트의 허용 상태를 인자화, (b) `approved_design_for_handoff` 같은 병렬 게이트 추가, (c) 상태 요구를 승인 이력으로 대체 중 하나를 골라야 한다. (a)가 최소 변경이고 S1 계약을 깨지 않는다.

**디자인 재실행 경로가 없다.** `require_approved_handoff`는 봉투 상태가 `APPROVED`나 `IN_PROGRESS`일 것을 요구하는데 `run_design`은 끝에 `COMPLETED`로 옮긴다. `HANDOFF_TRANSITIONS[COMPLETED] = {SUPERSEDED}`이므로 완료된 봉투로는 다시 실행할 수 없고, 프로젝트 상태 게이트도 막는다. Gate C 반송이나 QA 반송으로 디자인을 다시 돌려야 하는 S5에는 이 경로가 필수다.

**승인 2(시안 승인)가 없다.** 가이드 §2 제품 원칙 3의 세 승인 중 두 번째, §6의 `POST /artifacts/{type}/approve`가 구현되지 않았다. `DESIGN_APPROVED`는 `S2_TRANSITIONS`에 있지만 도달시키는 코드가 없다. S2 성공 조건에 명시되진 않았으니 의도된 미구현일 수 있지만, `DESIGN_REVIEW`에서 멈춘 프로젝트는 S3로 갈 방법이 없다.

**프로젝트 상태가 파이프라인을 구동하지 않는다.** `approve_handoff`는 프로젝트를 `PLANNING_APPROVED`에 남기는데(handoff.py:588-593), 이유는 S1의 게이트가 상태 기반이기 때문이다 — 주석에 그 이유가 정직하게 적혀 있다. 그 결과 인계가 승인된 프로젝트와 아직 인계하지 않은 프로젝트가 상태로 구별되지 않고, `DESIGN` 상태는 `run_design` 한 호출 안에서 들어갔다 나오므로 외부에서 관측되지 않는다. 실질적으로 파이프라인을 굴리는 것은 handoff status이고 프로젝트 상태는 따라가는 라벨이다. 부서가 늘어날수록 이 이중 진실이 비싸진다. S3 착수 전에 어느 쪽이 진실인지 정하는 게 낫다.

**개정 엔드포인트 부재.** S2가 추가한 엔드포인트는 `POST /handoffs`, `GET /handoffs`, `POST /handoffs/{id}/approve`, `POST /departments/design/run`, `GET /artifacts`, `GET /artifacts/{type}` 여섯 개다. 개정 엔드포인트가 없으므로 stale 전파와 supersede는 테스트에서만 실행된다. S5의 반송 루프가 개정에 의존하므로 그때까지 그 API 계약은 검증되지 않은 상태로 남는다.

## 사소한 것들

`routes.py` 모듈 docstring은 "라우터를 의도적으로 `main`에 include하지 않았다"고 말하고, 같은 파일 S2 섹션 주석은 "S1이 이미 include했다"고 말한다. `main.py:1387-1389`가 실제로 include한다. 다음 사람은 읽는 순서상 첫 문장을 먼저 믿게 된다.

`_payload`가 행마다 `HandoffEnvelope`를 구성하므로 DB에 이상한 값이 들어가면 `list_handoffs`가 pydantic `ValidationError`로 500이 된다. `coerce_handoff_status`처럼 명시적으로 실패시키는 편이 일관된다.

`derive_constraints`는 `technicalDirection.auth`가 `none`/`later`면 "로그인 화면 없이 진행"을 넣지만, `_screen_kind`는 Must 기능 이름에 `로그인`/`인증`/`회원`이 있으면 auth 화면을 만든다(design.py:66). 두 규칙이 같은 blueprint에서 모순될 수 있다 — 그런 blueprint를 S1이 만드는지는 확인하지 못했다 (possible).

`/api/vibe/*` 전체에 인증이 없고 `POST /projects`의 `workspace_path`가 검증 없이 파일 쓰기 루트가 된다. S1에서 넘어온 성질이라 이 리뷰 범위 밖이지만, S2가 쓰기 표면을 `docs/`와 `.vibeoffice/handoffs/`로 넓혔다는 점은 기록해 둔다. 경로 이탈 검사(`is_relative_to`)는 두 writer 모두에 있고 파일명이 상수라 traversal 자체는 막혀 있으며, 저장 경로는 상대 경로뿐이어서 가이드 §11의 절대경로 금지는 지켜진다.
